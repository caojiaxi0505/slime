# 朴素 GRPO：8 卡与 16 卡的时间 / `exit_code` / `resolved_rate` 对比

日期：2026-07-16

## 1. 结论

在两边都有数据的 step 0–20，共 21 个 step、每边 2,688 个 episode：

| 指标 | 8 卡 | 16 卡 | 16 卡相对 8 卡 |
|---|---:|---:|---:|
| `exit_code=-1` | 420（15.63%） | 372（13.84%） | -1.79 个百分点 |
| `exit_code=0` | 1,960（72.92%） | 1,851（68.86%） | -4.06 个百分点 |
| `exit_code=1` | 299（11.12%） | 450（16.74%） | +5.62 个百分点 |
| `exit_code` 缺失 | 9（0.33%） | 15（0.56%） | +0.23 个百分点 |
| resolved | 1,551（57.70%） | 1,526（56.77%） | -0.93 个百分点 |
| episode 平均已记录 agent 时间 | 10.29 分钟 | 13.74 分钟 | +3.45 分钟 |
| 相邻 dump 平均间隔 | 60.98 分钟 | 77.90 分钟 | +16.92 分钟 |

16 卡的超时退出（`-1`）比例更低，但正常退出（`0`）比例也更低；差额主要转移到了
非零退出（`1`）。两边总体 `resolved_rate` 接近，16 卡低 0.93 个百分点。

逐 step 看，16 卡有 7 个 step 的 `resolved_rate` 更高、1 个相同、13 个更低。单步差值
介于 -10.94 到 +9.38 个百分点，说明单个 step 的波动明显大于整个共同区间的 0.93 个
百分点差值。

这不是只改变 GPU 数量的严格对照实验：8 卡任务使用 30 分钟 agent budget，16 卡任务使用
45 分钟 agent budget 和并发上限 64。因此本文只报告这两份 run 的观测差异，不能把差异
单独归因于 GPU 数量。

## 2. 数据范围与统计口径

### 2.1 数据来源

| 配置 | step | rollout dump |
|---|---:|---|
| 8 卡朴素 GRPO | 0–21 | `qwen35_9b_cc_ags_1node_grpo_debug/rollout_dumps/rollout_{step}.pt` |
| 16 卡朴素 GRPO | 0–9 | `qwen35_9b_cc_ags_2node_grpo_c64_t45/rollout_dumps/rollout_{step}.pt` |
| 16 卡朴素 GRPO | 10–20 | `qwen35_9b_cc_ags_2node_grpo_c64_t45_resume10_adapterfix/rollout_dumps/rollout_{step}.pt` |

按运行时间线，16 卡 step 0–9 是修复前，step 10 及之后是修复后。本文不比较或解释
修复前后，只将它作为数据来源边界记录下来。汇总结论只使用两边都存在的 step 0–20；
8 卡独有的 step 21 仅保留在逐 step 表中。

### 2.2 指标定义

- 每个 `session_id` 只计为一个 Claude Code episode。compact 产生的多个 segment 不重复计数。
- 每个 step 都有 128 个有效 episode。
- `resolved_rate = grading_solved=true 的 episode 数 / 128`。
- `exit_code=-1`：agent 达到时间预算；`0`：进程正常退出；`1`：进程以非零状态退出；
  “缺失”表示 rollout metadata 中没有该字段。
- `exit_code` 描述 Claude Code 进程如何结束，`resolved` 描述最终评测是否通过，两者不是
  同一个指标。
- `agent_elapsed_sec` 使用 rollout 中的原始记录。16 卡 step 0–9 的旧计时位置会把并发槽
  排队计入该字段；step 10+ 不计排队。本文列出原值，不据此分析修复前后。
- “相邻 dump 间隔”是 `rollout_n.pt` 与前一份 dump 的文件落盘时间差，包含 rollout、评测、
  参数更新和调度开销，不等于单个 episode 的执行时间。

## 5. 结果解读

### 5.1 `exit_code` 分布

共同区间内，16 卡的 `-1` 比 8 卡少 48 次，但 `0` 也少 109 次，`1` 多 151 次。
因此不能只根据超时比例判断 16 卡的 agent 完成情况更好：16 卡减少的超时退出并没有全部
转化成正常退出，更多表现为非零退出。

两份 run 的 exit 分布都随 step 明显变化，不能用某一个 step 代表整段训练。例如 step 8–9
的 16 卡 episode 全部为 `0`，而 step 17–20 的 `-1` 分别为 75、61、82、63。本文只记录
该现象，不将变化解释为修复效果。

### 5.2 `resolved_rate`

共同区间汇总后，8 卡为 57.70%，16 卡为 56.77%。0.93 个百分点的总体差值较小，且逐 step
没有形成始终由某一侧领先的关系。因此现有数据支持的结论是：这两份 run 的整体
`resolved_rate` 接近，不能据此认定 16 卡本身提高或降低了解题能力。

`exit_code` 与 `resolved_rate` 也不能直接互相替代。进程正常退出不代表补丁一定通过测试；
达到时间预算的 agent 也可能已经写出可通过评测的补丁。判断训练产出仍应以
`resolved_rate` 为准，`exit_code` 用于描述运行完成方式。
